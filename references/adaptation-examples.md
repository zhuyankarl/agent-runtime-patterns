# 跨场景适配示例

以下是运行契约的形态选择参考，不是要求安装新组件。优先使用目标项目现有设施。

## 文件、配置表和代码变更

需求 → 候选变更清单 → 校验 → 差异预览 → 应用 → 读回验证。

- 模型理解需求、提出字段/行修改；程序处理主键、类型、范围、引用和应用操作。
- 候选清单记录文件及记录标识、预期旧值/基线摘要、新值、依据；限制可写目标与字段。
- 应用前检查基线，避免覆盖他人修改。使用现有文件库、备份或临时文件机制；多文件不能只凭逐个替换宣称整批原子性。
- 保存逐项回执和恢复信息。失败时明确哪些文件已修改，恢复前重新检查，避免回滚掉别人的后续修改。
- 版本库提交、发布或上传是另外的副作用，严格沿用项目规则及用户授权。

## 数据库批处理

待处理记录 → 领取任务 → 模型候选结果 → 校验 → 事务应用 → 结果核对。

- 使用数据库支持的任务领取和并发控制，避免用无锁读取状态替代互斥。
- 业务记录和进度/关键审计可以在同一事务中提交；任务 ID/业务键的唯一约束用于防重复。
- 同一事务以外的通知、消息或 API 调用需要单独处理一致性；可复用既有 outbox 等机制。
- 数据库状态用于恢复，模型会话只提供本次任务的必要上下文。

## 外部 API 与业务系统

输入快照 → 建议操作 → 授权范围与载荷校验 → API 调用 → 回执/读回对账。

- 明确操作是否已获用户授权；Skill 不把生成建议等同于允许实际发送或发布。
- 服务支持幂等键时使用稳定的业务操作键。查询/版本条件应按实际 API 能力设计，不能假设存在。
- 超时或连接断开可能发生在服务端已处理之后；查询结果后再决定重试。
- 不支持幂等、查询或撤销时，缩小自动应用范围，对未知结果停止盲目重试并交接。

## 队列和事件驱动流程

消息 → 去重/领取 → 候选结果 → 校验和应用 → 持久回执 → 确认消息。

- 消息可能重复；根据队列实际语义设计消费确认、重试、死信和背压。
- 多个 worker 可处理互不冲突的任务，对同一目标使用并发约束。
- 消息确认与外部写入通常不是同一事务，不直接宣称端到端 exactly-once。
- Schema 版本与兼容策略也是上下游契约；通过状态交换不等于完全没有耦合。

## 纯读报告与资料整理

采集快照 → 清洗/统计 → 模型解释或摘要 → 来源及数字校验 → 输出报告。

- 统计、差异和排序优先由代码完成，模型负责需要判断的部分。
- 没有正式业务写入时，无需增加提交服务、数据库事务或复杂状态机。
- 需要跨日对比或断点恢复时，保留快照和处理记录即可；手动入口可能已经足够。

## 组合原则

共享可靠的工具库是正常复用，不必为了“agent 解耦”复制代码。需要减少的是隐式业务依赖、共享可变状态和未声明的交付契约。

业务不变量必须保留，例如价格不能为负、资源引用必须存在、权限范围不可扩大。“通用 runtime”不意味着禁止领域校验。
