# 运行契约模板

复制需要的部分到目标项目已有设计文档；不要强制创建一套新目录。以下字段用于作出可执行决策，留空项应标为“不适用”或“待验证”，并说明是否影响实施。

## 1. 任务与边界

- 要消除的实际失败模式：
- 输入来源、任务选择条件及范围：
- 成功的可观察定义：
- 当前授权允许哪些读写、副作用：
- 生成端和应用端分别持有哪些权限：
- 不属于本次工作的内容：

## 2. 数据契约

| 对象 | 应明确的内容 |
|---|---|
| 输入快照 | 来源、稳定标识、版本或摘要；必要的上下文 |
| 候选产物 | schema 版本、任务关联、模型提出的修改/判断及证据 |
| 校验回执 | 校验器版本、检查集合、通过/失败/未执行、原因、对应产物摘要 |
| 应用回执 | 幂等键、目标版本、实际影响范围、持久化回执、结果是否确定 |
| 运行记录 | run_id、attempt、时间、输入与产物版本、数量、错误和恢复位置 |

程序从可信状态取得任务范围和目标权限，不允许模型通过在 JSON 中添加任意目标、SQL 或命令来扩大权限。

并非所有任务都需要全部字段；纯读任务无需应用回执。必要 provenance 可以只包含模型/提示词版本和输入摘要，无需记录模型的私有思维链或不必要的敏感原文。

## 3. 确定性规则和模型判断

- 模型必须判断的部分，以及允许的不确定结果：
- 由代码承担的计算、ID、状态变更和写入：
- 程序拒收规则：
- 需要业务样本/人工验证的质量标准：

结构合法、证据存在、判断正确分别验证。缺少信息可以进入待补充状态，不应一律转成业务否定结论。

## 4. 状态与恢复

可参考但无需照搬的状态：

pending → running → candidate_ready → validated → applied

按场景增加 needs_review、retry_wait、failed、partial、unknown。dry_run_passed 是预演结果，不应与 applied 混淆；预演完成不一定表示业务任务已消费。

对每个可能中断点回答：

| 问题 | 决策 |
|---|---|
| 重跑如何识别同一业务任务？ | 去重键及有效范围 |
| 谁能领取或提交这个任务？ | 所有者、租约/锁/条件更新及过期执行者处理 |
| 进程中断后从哪里恢复？ | 持久状态、产物和回执位置 |
| 外部操作超时但可能已成功？ | 查询/对账机制；何时允许重试 |
| 部分条目成功？ | 成功条目记账，剩余条目继续或补偿 |
| 永久错误或毒任务？ | 尝试上限和人工处理入口 |

不要将“事务内先读状态，再普通更新”称为充分的乐观锁。应验证原子条件更新的受影响行数、版本冲突或等价的数据库并发机制。

## 5. 应用与一致性

- 预演关联的输入/目标版本和产物摘要：
- 应用时必须重新检查的条件：
- 事务覆盖的对象及不覆盖的副作用：
- 重复调用的可观察行为：
- 回滚、补偿或前向修复的适用条件：
- 应用后读回和对账方式：

“可回放”仅表示可复用保存的输入/产物；不意味着可以安全重复外部副作用。补偿可能失败，必须定义可见状态和后续处置。

## 6. 运行、验收和交接

- 触发方式及运行环境：
- 资源/时间限制与重试策略：
- 状态变化、错误和结果证据存放位置：
- 选择的验证场景及实际结果：
- 可安全运行的预演入口：
- 正式应用入口及已有授权前提：
- 中断恢复入口、未完成项和影响：

交给其他 agent 时，一并给出契约、相关代码入口、输入/产物位置和验证记录。不要仅传上一段对话总结，也不要携带凭据。
